# 条目改造与骨架模板

## 条目改写规范

知识条目的目标形态是"可执行判定"，不是"可阅读文档"。统一为四元组：
**触发条件 + 严重级别 + 反例 + 正例**。

触发条件必须挂在输入的可观察特征上（文件类型、任务阶段、关键词、代码特征等），
凡是需要模型"领会精神"的表述都不合格。

改写三原则：
- 一组 bad→good 对照，胜过十条抽象原则——模型从对照中学到的是判定边界
- 叙事、背景、动机全部删掉，只留判定规则与示例
- 严重级别固定三档：P0（违反即阻断）、P1（应默认执行）、P2（风格倾向）

## Before / After 示例

改造前（人类文档式，约 80 词，不可判定）：

> 报告应当覆盖任务的核心要求，注意不要遗漏隐含的边界条件，格式要统一，
> 优先级排序要合理，对不确定的结论应当标注置信度……

改造后（agent 可执行式，以数据分析 skill 为例）：

```markdown
[P1] 结论必须绑定数据来源
  触发: 输出中出现数字/比例/趋势判断
  反例: "转化率明显下降了。"
  正例: "转化率从 3.2% 降至 2.1%(来源: funnel.csv, 9月 vs 8月)。"

[P0] 缺失数据必须显式声明而非臆造
  触发: 请求的指标在输入数据中无对应字段
  反例: 估算一个数字写进结论
  正例: "DAU 缺失(输入无该字段),需补充埋点数据后才能给出。"
```

（代码评审领域的同类改写见 optimization-rulebook.md RB-02/RB-04。）

## 路由表设计

references/ 的拆分单位是"输入的触发特征"，不是知识的学科归属。
按学科拆（命名/日志/安全各一份）的后果是每次都要全量加载；
按特征拆则一次运行通常只命中一两个文件。路由表直接写在 SKILL.md 正文：

```markdown
- 输入含 <特征A: 文件类型/任务阶段/关键词> → 读 references/<a-standards>.md
- 输入含 <特征B> → 读 references/<b-standards>.md
- 任何输入 → 读 references/<always>.md(精简版,始终加载)
```

例(代码评审 skill):`diff 含 SQL/事务注解 → 读 references/db-standards.md`；
例(写作 skill):`需求含"对外发布/公告" → 读 references/tone-public.md`。

## 两阶段执行模式

适用于"先收集事实、后输出结论"的分析型任务（评审、审计、调研、写作前
素材收集等），让 checklist 退到第二阶段，不挤占第一阶段的深度推理：

```
Pass 1(深度推理,不加载任何规范文件)
  → 通读输入,自由推理,聚焦需要推理的高价值维度
  → 产出候选问题清单

Pass 2(定向扫描,只加载路由命中的 references)
  → 逐项核对候选问题 + 按规范补充遗漏
  → 输出:P0/P1 逐条列出;P2 合并为一段汇总,不逐条展开
```

## SKILL.md 骨架模板(可直接套用)

```markdown
---
name: <verb-ing-noun,小写连字符>
description: <第三人称,一句话说明做什么 + 触发场景与关键词,1024 字符内>
agent_created: true
---

# <Skill 标题>

<一句话信念声明:这个 skill 相信什么>

## 执行流程(按序执行)
1. <步骤: 输入动作 → 产出物>
2. <步骤>
3. ...

## 路由表(仅加载命中项)
- <输入特征> → 读 references/<file>.md
- <输入特征> → 读 references/<file>.md
- 任何输入 → 读 references/<always>.md

## 优先级框架
- P0: <阻断性问题> —— <输出要求>
- P1: <重要问题> —— <输出要求>
- P2: <风格类> —— 合并汇总,不逐条展开

## 输出格式
<固定模板>

## 硬性红线
- <不超过 5 条>
```
