# 条目改造与骨架模板

## 条目改写规范

每条知识条目统一为四元组:触发条件 + 严重级别 + 反例 + 正例。
触发条件必须可由输入直接观察到(文件类型、任务阶段、关键词、代码特征等),
不可依赖主观判断。

改写原则:
- 一个 bad→good 示例对的效力大于十条抽象原则
- 删除所有叙事性解释、背景、理由——只留判定规则和示例
- 严重级别只用三档:P0(必须执行/阻断性)、P1(强烈建议)、P2(风格偏好)

## Before / After 示例

改造前(人类文档式,约 80 词,信息密度低):

> 报告应当覆盖任务的核心要求,注意不要遗漏隐含的边界条件,格式要统一,
> 优先级排序要合理,对不确定的结论应当标注置信度……

改造后(agent 可执行式,以数据分析 skill 为例):

```markdown
[P1] 结论必须绑定数据来源
  触发: 输出中出现数字/比例/趋势判断
  反例: "转化率明显下降了。"
  正例: "转化率从 3.2% 降至 2.1%(来源: funnel.csv, 9月 vs 8月)。"

[P0] 缺失数据必须显式声明而非臆造
  触发: 请求的指标在输入数据中无对应字段
  反例: 估算一个数字写进结论
  正例: "DAU 缺失(输入无该字段),需补充埋点数据后才能给出。"
```

(代码评审 skill 的同类改写示例见 optimization-rulebook.md RB-02/RB-04。)

## 路由表设计

references/ 按"触发特征"拆分,不按"学科"拆分。
学科式拆分(命名规范/日志规范/安全规范)导致每次全量加载;
特征式拆分让每次只命中一两个文件。路由表写在 SKILL.md 正文中,格式:

```markdown
- 输入含 <特征A: 文件类型/任务阶段/关键词> → 读 references/<a-standards>.md
- 输入含 <特征B> → 读 references/<b-standards>.md
- 任何输入 → 读 references/<always>.md(精简版,始终加载)
```

例(代码评审 skill):`diff 含 SQL/事务注解 → 读 references/db-standards.md`;
例(写作 skill):`需求含"对外发布/公告" → 读 references/tone-public.md`。

## 两阶段执行模式

适用于需要先收集事实再输出结论的分析型 skill(评审、审计、调研、写作前素材收集等),防止 checklist 挤占深度推理:

```
Pass 1(深度推理,不加载任何规范文件)
  → 通读输入,自由推理,聚焦需要推理的高价值维度
  → 产出候选问题清单

Pass 2(定向扫描,只加载路由命中的 references)
  → 逐项核对候选问题 + 按规范补充遗漏
  → 输出:P0/P1 逐条列出;P2 合并为一段汇总,不逐条展开
```

## SKILL.md 骨架模板(可直接套用)

```markdown
---
name: <verb-ing-noun,小写连字符>
description: <第三人称,一句话说明做什么 + 触发场景与关键词,1024 字符内>
agent_created: true
---

# <Skill 标题>

<一句话说明核心原则/价值观,回答"这个 skill 相信什么">

## 执行流程(按序执行)
1. <步骤: 输入动作 → 产出物>
2. <步骤>
3. ...

## 路由表(仅加载命中项)
- <输入特征> → 读 references/<file>.md
- <输入特征> → 读 references/<file>.md
- 任何输入 → 读 references/<always>.md

## 优先级框架
- P0: <阻断性问题> —— <输出要求>
- P1: <重要问题> —— <输出要求>
- P2: <风格类> —— 合并汇总,不逐条展开

## 输出格式
<固定模板>

## 硬性红线
- <不超过 5 条>
```
